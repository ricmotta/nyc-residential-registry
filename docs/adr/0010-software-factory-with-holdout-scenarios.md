# Software factory: Holdout Scenarios gate agent work, the owner keeps critical decisions

We want agents to take a ticket from spec to a ready pull request with as little human effort as possible, in the spirit of the "dark factory" pattern (Saumya Tyagi, "The Dark Factory Pattern", HackerNoon, 2026). This is a personal project, so we adopt the parts that raise quality cheaply and skip the parts that need paid infrastructure.

## Target

Reach Level 3 first: an agent implements a ticket, Holdout Scenarios decide whether the result is correct, and the owner reads a short Holdout Report and merges. Level 4 (auto-merge) comes later and only per category of change, starting with low-risk ones such as documentation. Auto-merge is considered only after 20 consecutive pull requests where the Holdout Report and the owner's verdict agreed.

These always need the owner, at every level: Terms Status changes (`docs/source-catalog.md`), Owner Decisions (dbt seeds), Review Queue decisions and ADRs.

## Holdout Scenarios

- **Isolated from the coding agent.** They live in a separate private repository (`nyc-residential-registry-holdout`, to create), cloned outside this working directory. The coding session has a permission rule that denies reading it. This isolation relies on permissions and discipline, not on a hard barrier; that is enough for a personal project.
- **Written before the code.** A separate session, opened in the holdout repository and never shown the implementation, drafts scenarios from the ticket and official Sources. Each scenario has a status: `draft`, `confirmed` (by the owner, fact by fact) and `retired`. Only `confirmed` scenarios count, and only the owner retires one, with a reason. A fact generated by the same agent that writes the code would make the test circular.
- **Only for data tickets.** Tickets that create or change data in Silver or Gold start with `Holdout: required` and get `ready-for-agent` only after their scenarios are `confirmed`. Infrastructure and documentation tickets say `Holdout: not needed` and rely on CI.
- **Deterministic SQL facts, run once.** For example, "Tax Lot X has 6 floors" or "this address links to this Building". No LLM judges the result, so there is no need for repeated runs.
- **Gold first, Silver through stable surfaces.** Each scenario declares `layer: gold` or `layer: silver`. Gold alone would miss matching links, per-Source Claims, Quarantine, the Review Queue and redirects, and two errors could cancel out in a final value. Silver scenarios read only the Claims view, matching links, Quarantine, the Review Queue export and redirects, never satellites directly, so refactoring internals does not break scenarios. Bronze stays with pytest.

## Flow per data ticket

1. Scenarios `confirmed` in the holdout repository.
2. The coding session implements the ticket, runs the checks and self-reviews with the `code-review` skill (default effort), then opens the pull request with a short self-review summary.
3. The evaluator session, opened in the holdout repository, checks out the branch, runs the local environment (`docker compose`) and the pipeline, runs the scenarios and comments a Holdout Report on the pull request. Because the main repository is public, the report shows scenario IDs and fields only, never expected values.
4. Gate: 100% of `confirmed` scenarios pass. On failure the coding session gets only the report lines and tries again on the same branch, at most 2 attempts in total; then it labels the ticket `ready-for-human` with a summary of what it tried.
5. The owner merges or not. The evaluator records one row per pull request in a CSV in the holdout repository: `pr`, `date`, `scenarios_passed`, `scenarios_total`, `owner_verdict` (`merged`, `changes_requested`, `closed`), `agreed` (`yes` or `no`) and `reason` (required when `agreed = no`). `agreed = yes` means the report and the owner's verdict pointed the same way. A `no` resets the count of 20.

## Cheaper guardrails adopted now

- A versioned Git `pre-push` hook runs the four CI checks, so a broken push is caught before CI.
- ruff `banned-api` rules with instructive messages keep `boto3`, `httpx` and `psycopg` inside their own modules (ADRs 0002 and 0006). A pytest test will enforce "never delete in Bronze" once the first collector exists.

## Not adopted, for now

- Cloud ephemeral environments, LLM evaluators with 2-of-3 runs and a paid orchestrator calling a model API: too costly for a personal project. The local Docker environment plays the ephemeral environment.
- Running scenarios in GitHub Actions across both repositories: revisit at Level 3.5 or 4, when merging must happen without the owner.
- A scheduled weekly maintenance agent: maintenance sweeps run on demand; revisit at Level 3.5.
